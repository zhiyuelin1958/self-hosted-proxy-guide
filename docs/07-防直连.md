# 07 防直连（可选）

## 1. 问题：客户端一关，流量就“漏”回本地

分流只在客户端运行时生效。Karing 关闭、崩溃或开机后还没启动时，所有程序都回到本地网络直连。这样一来，第 06 章的指定服务会看到同一个账号时而从第二出口、时而从本地 IP 访问。

**防直连的目标**：在客户端之外再固定一条路径，指定服务只能走这条路径。路径不通时连接直接失败（fail-closed），不回退直连。

| 层 | 设备 | 原理 | 难度 |
|---|---|---|---|
| A | Windows 的 Chrome / Edge | 浏览器策略强制这些域名只走本地代理端口 | 低 |
| B | iPhone | 系统级“网络中继”描述文件，强制这些域名走服务器上的独立中继 | 高 |
| C | WSL / Linux 命令行工具 | 启动前检查出口，不符合就不启动 | 低 |

保护名单都用第 06 章的同一份域名清单。

## 2. A 层：Windows Chrome / Edge 浏览器策略

### 原理

Chrome 和 Edge 支持通过注册表下发“企业策略”。脚本 [client/windows/browser-fail-closed.ps1](../client/windows/browser-fail-closed.ps1) 写入两项策略（仅当前 Windows 用户）：

| 策略 | 值 | 作用 |
|---|---|---|
| `ProxySettings` | 内嵌 PAC 脚本，`ProxyPacMandatory=true` | 名单内域名 → 只返回 `PROXY 127.0.0.1:3067`，**没有 `DIRECT` 备用**；其他域名 → `PROXY 127.0.0.1:3067; DIRECT`，代理不在时还能直连 |
| `WebRtcIPHandling` | `disable_non_proxied_udp` | WebRTC 不得绕过代理发 UDP，避免泄露本地 IP |

PAC 以 `data:` URL 的形式内嵌在策略里，不依赖本地文件，也不需要下载。`ProxyPacMandatory` 保证 PAC 出错时不会退回直连。

Karing 关闭后 `3067` 端口不再监听，名单内域名在浏览器里就会报“代理连接失败”，而普通网站照常直连。

### 安装

以管理员身份打开 PowerShell，在仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\client\windows\browser-fail-closed.ps1 `
  -Action Install -DomainsFile .\templates\protected-domains.example.json -Port 3067
```

脚本首次安装时会备份原有策略到 `%LOCALAPPDATA%\ProxyFailClosed\`。重启浏览器，或打开 `chrome://policy`、`edge://policy` 点“重新加载策略”。

回退：把 `-Action Install` 改为 `-Action Remove`，恢复安装前的策略。

### 验收

1. Karing 开启：名单内检测站显示第二出口，普通网站正常；
2. 退出 Karing，确认 `3067` 不再监听、系统代理已关闭：

   ```powershell
   Get-NetTCPConnection -LocalPort 3067 -State Listen -ErrorAction SilentlyContinue
   ```

3. 浏览器打开名单内网站 → 应报代理连接错误；打开普通国内网站 → 正常；
4. 重新开启 Karing → 恢复第二出口。

### 局限

- 只覆盖 Chrome / Edge，不覆盖其他浏览器和桌面程序；
- 每个 Windows 用户需分别安装；
- 名单变化后需重新执行安装；
- Karing 的“始终开启连接”只负责自动重连，主动断开后它不提供保护。

## 3. B 层：iPhone 系统中继（进阶）

### 原理

iOS 17 起支持“网络中继”（[Apple Relay 描述文件](https://developer.apple.com/documentation/devicemanagement/relay)，类型 `com.apple.relay.managed`）。对 `MatchDomains` 中的域名，系统直接通过指定的 HTTP/2 或 HTTP/3 中继发起连接，和 Karing 是否开启无关。设置 `AllowDNSFailover=false` 后，中继不可用时连接直接失败。

所以我们在入口服务器上另起一个独立中继，它的所有出站都强制走第二出口：

```text
iPhone（MatchDomains 内的域名）
   │ HTTP/2 CONNECT，TLS，Proxy-Authorization
   ▼
入口服务器 :8443 ── Xray dokodemo-door（仅转发）
   ▼
网络命名空间 app-relay 内的 Envoy（10.231.252.2:18443）
   │ 认证 + CONNECT / CONNECT-UDP 动态转发
   ▼  （命名空间内所有出站都被 TPROXY 截走）
Xray dokodemo-door :18445（tproxy）── socks 出站 exit2
   ▼
第二出口 ──► 目标服务
```

几个设计要点：

| 设计 | 目的 |
|---|---|
| Envoy 放在独立网络命名空间里 | 它没有直接上网的路径。命名空间的所有出站都经 TPROXY 交给 Xray 的 `exit2`，第二出口挂掉时只能失败 |
| 命名空间内拒绝私有网段 | 中继不能被用来访问服务器内网 |
| 独立的 systemd 单元和独立的 Xray 进程 | 和第 04 章的主 Xray 互不影响，可以单独停用 |
| 公网可信的 IP 证书 | iOS 要求中继的 TLS 证书可信；没有域名时可用 Let's Encrypt 的 IP 地址证书（6 天短期证书，自动续期） |
| 每用户一组账号密码 | 写进各自的描述文件，Envoy 校验 `Proxy-Authorization` |
| 描述文件下载路径带随机令牌 | 不需要另建网站，Envoy 直接返回 `.mobileconfig` |
| 不含根证书、不需要 MDM | 普通 iPhone 手动安装即可，移除描述文件即解除 |

### 部署步骤

脚本在 [server/relay/](../server/relay/)。先阅读该目录的 [README](../server/relay/README.md)，再按顺序操作：

1. 编辑 `relay_settings.py`，填入 `PUBLIC_HOST`（服务器 IP）和 `EGRESS_TAG`（主配置中第二出口的 tag，默认 `exit2`）；
2. 把 `server/relay/` 和保护名单复制到服务器，`sudo python3 prepare_relay.py`：下载并校验 Envoy、生成账号、写配置和 systemd 单元，**不启动服务、不开端口**；
3. 放行 80（证书验证）和 8443（中继）：云安全组 + `sudo ufw allow 80/tcp && sudo ufw allow 8443/tcp`；
4. 申请 IP 证书（需要 Certbot ≥ 5.4，用独立虚拟环境安装，避免与系统包冲突）：

   ```bash
   sudo python3 -m venv /opt/app-relay/acme
   sudo /opt/app-relay/acme/bin/pip install 'certbot>=5.4'
   sudo /opt/app-relay/acme/bin/certbot certonly --standalone \
     --preferred-profile shortlived --ip-address <SERVER_IP> \
     --cert-name app-relay-ip -m <你的邮箱> --agree-tos
   ```

   先加 `--staging` 试一次更稳妥。IP 证书只有约 6 天有效期，所以续期定时器每天检查两次；80 端口在续期时也必须可达。
5. `sudo python3 enable_renewal.py`：安装续期钩子和定时器，复制证书，启动 `app-relay.target`；
6. 先用测试描述文件（只匹配 `www.cloudflare.com`）在手机上验证，再 `sudo python3 publish_profiles.py --publish` 生成正式描述文件，输出里有每位用户的下载链接。

### 在 iPhone 上安装与验收

1. 用 Safari 打开自己的下载链接 → 允许下载 → “设置 → 已下载描述文件” → 安装；
2. 保持系统中继启用；
3. 分别在 Karing 开启和关闭两种状态下打开检测页，都应显示第二出口；
4. 关闭 Karing 后测试 App 收发新消息。**切换后 App 卡住时，完全退出再重新打开**（已建立的连接不会自动迁移）；
5. 故障演练：在服务器上 `sudo systemctl stop app-relay-egress.service`，确认名单内网站和 App 都无法连接、普通网站正常；然后 `sudo systemctl start app-relay.target` 恢复。

### 局限

- 按域名生效，名单变化后要重新发布，并在手机上重新安装；
- 移除描述文件即解除保护；
- 中继服务或第二出口不可用时，名单内服务在手机上不可用（这是设计目标）。

## 4. C 层：命令行工具的启动前检查（WSL / Linux）

### WSL 网络准备

Windows 11 22H2 及以上，在 `%USERPROFILE%\.wslconfig` 中加入（已有 `[wsl2]` 节就合并），见 [client/wsl/wslconfig.example](../client/wsl/wslconfig.example)：

```ini
[wsl2]
networkingMode=mirrored
autoProxy=true
dnsTunneling=true
```

PowerShell 执行 `wsl --shutdown` 后重新进入。效果：

| 选项 | 作用 |
|---|---|
| `mirrored` | WSL 与 Windows 共享网络，可通过 `127.0.0.1` 访问 Windows 上的 Karing |
| `autoProxy` | WSL 自动继承 Windows 的系统代理（`http://127.0.0.1:3067`） |
| `dnsTunneling` | DNS 交给 Windows 处理，受 Karing 的 DNS 分流控制 |

先开启 Karing 的系统代理、TUN 与严格路由，再使用 WSL。参考 [Microsoft WSL 网络说明](https://learn.microsoft.com/windows/wsl/networking)。

### 启动前检查脚本

[client/wsl/egress-guard.sh](../client/wsl/egress-guard.sh) 在启动某个命令前，请求一个检测地址，最多等待几秒；只有返回的 `ip` 和 `loc` 都符合预期才执行命令，否则退出：

```bash
sudo install -m 755 client/wsl/egress-guard.sh /usr/local/bin/egress-guard
# 用法：egress-guard <检测URL> <期望IP> <期望地区> -- <命令> [参数...]
egress-guard https://www.cloudflare.com/cdn-cgi/trace 203.0.113.10 JP -- curl -I https://example.com
```

可以为常用工具写一个同名包装脚本，放在 `PATH` 中优先于原程序的位置（如 `/usr/local/bin/<工具名>`），内部调用 `egress-guard ... -- /真实/路径/<工具名> "$@"`。注意：

- 它**只在启动前检查**，运行中仍须保持 Karing 连接，不等于持续断网保护；
- 工具自身的升级程序可能覆盖包装脚本，升级前备份、升级后恢复，并关闭工具的自动更新。
